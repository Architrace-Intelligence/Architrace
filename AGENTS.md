# AGENTS.md

Operating instructions for AI coding agents working in this repository.
Humans are welcome to read it too: it is the shortest accurate description of how this project is run.

## 1. Mission

Architrace is an open-source, AI-centric platform for observing, visualising and improving the
runtime architecture of a company: services, data streams, dependencies, drift between
environments and releases, and architecture insights derived from telemetry.

The project owner and sole maintainer is **Dmytro Hryshchenko** (`@godmarch33`,
organisation `Architrace-Intelligence`). Every commit, pull request and document is authored
by the maintainer. Agents never add their own attribution, co-author trailers, signatures,
badges or "generated by" notes anywhere: not in commits, PR bodies, code, docs or release notes.

## 2. Communication

- Talk to the maintainer in **Russian**.
- Everything that lands in the repository (code, comments, commit messages, PR titles and
  bodies, documentation, ADRs, issues) is written in **English**.
- The maintainer wants to learn from the work: every non-trivial PR explains what was done
  technically and names the patterns and approaches used and why.
- This repository is public. Never reference the maintainer's employer, internal systems,
  internal hostnames, ticket systems or private repositories in code, docs or PRs.

## 3. Workflow

Development is feature-driven and PR-only.

1. Agree the feature scope with the maintainer (it must exist in the Requirements page or be
   explicitly requested).
2. Record architectural decisions as ADRs under `DOCS/project/adr/` **only after the maintainer agrees**.
3. Branch from `main`: `ARCHI-<n>-<short-topic>`. Ticket numbers are sequential: the next
   number is one above the highest used in existing branches and PR titles.
4. Implement, test locally (all quality gates green), update docs.
5. Open a PR using `.github/PULL_REQUEST_TEMPLATE.md`; fill every section honestly.
6. CI runs the quality gates and CodeRabbit reviews the PR. Resolve every review thread
   (fix or answer), then the maintainer reviews and merges; the merge is the approval.
7. After merge the main pipeline builds, versions and publishes artifacts.

Never push directly to `main`. Never merge your own PR. Never force-push a shared branch.
Never push onto a merged branch: follow-up work gets a new branch and a new PR.

### Commit convention

Conventional Commits with the ticket as scope. The PR title must follow the same rule because
PRs are squash-merged and the title becomes the commit subject on `main`:

```
<type>(ARCHI-<n>): <Imperative subject>
```

| type       | version bump | use for                                              |
|------------|--------------|------------------------------------------------------|
| `feat`     | minor        | new user-visible capability                          |
| `fix`      | patch        | bug fix                                              |
| `perf`     | patch        | performance improvement                              |
| `refactor` | patch        | behaviour-preserving restructuring                   |
| `build`    | patch        | build system, dependencies                           |
| `ci`       | none         | pipelines, workflows                                 |
| `docs`     | none         | documentation only                                   |
| `test`     | none         | tests only                                           |
| `chore`    | none         | housekeeping                                         |

A `!` after the scope or a `BREAKING CHANGE:` footer bumps the major version.

### Documents that must stay current

All documentation lives on the documentation site (`documentation/architrace-inteligence/src/content/docs/`,
published to GitHub Pages from `main`). `DOCS` below means that folder.

| Page                              | Update when                                                  |
|-----------------------------------|--------------------------------------------------------------|
| `DOCS/project/state.md`           | after every feature or part of a feature, and before starting the next task |
| `DOCS/project/requirements.md`    | scope changes, new requirement discovered                    |
| `DOCS/project/progress.md`        | every stage or feature changes state                         |
| `DOCS/architecture.md`            | after every implementation PR that changes structure         |
| `DOCS/project/adr/`               | an architectural decision is agreed                          |
| `DOCS/project/features/<name>.md` | a feature is designed or its behaviour changes               |
| `DOCS/getting-started.md`, `DOCS/reference/`, `DOCS/guides/` | user-facing behaviour changes      |
| `README.md`                       | repository front page: commands or capabilities change       |

### Context hand-over

Conversations are feature-scoped, the agent's context may be reset at any moment and the
maintainer's machine may reboot. The repository is therefore the only memory that counts.

- `DOCS/project/state.md` is the hand-over page: where the work is, what is decided, what the
  next step is, how to resume. It describes the present only.
- Update it in the same commit as the work it describes: after a feature, after a meaningful
  part of a feature, and whenever a decision changes the plan.
- Before starting a new task, rewrite it: remove everything that is no longer needed to
  resume. Keep it short enough to read in one minute. History belongs in `progress.md` and git.
- Commit and push at every such boundary, even on a work-in-progress branch, so nothing lives
  only in a working tree or in a conversation.
- On session start: read `state.md`, run `git status` and `gh pr list --state open`, then
  continue from "Next step".

## 4. Engineering rules

- Java 25, Gradle Kotlin DSL, multi-module build (`architrace-api`, `architrace-agent`,
  `architrace-control-plane`, `architrace-ui`; project paths equal directory names) with the
  convention plugins of the included build `build-logic` (`architrace.java`,
  `architrace.spring-boot`, `architrace.versioning`). Preview features are enabled
  (`--enable-preview`).
- Principles in order of precedence: correctness, KISS, YAGNI, SOLID, clean code,
  data-oriented programming (records, sealed interfaces, pattern matching, immutable data,
  behaviour separated from data).
- Collection processing uses the Stream API (`map`, `filter`, `flatMap`, `Collectors.toMap` with
  a merge function, `groupingBy`, `IntStream.range` for index ranges). Explicit loops are
  reserved for control flow that is not a collection pipeline: polling, retries, batched I/O.
- **No documentation comments in code.** No Javadoc, no explanatory comments. Names, types
  and structure carry the meaning. The only allowed header is the SPDX license header enforced
  by Spotless; the copyright holder is `Dmytro Hryshchenko`.
- Prefer small, single-purpose classes; constructor injection; no static mutable state.
- Tests: JUnit 6, AssertJ, Mockito. Test behaviour through public API; never use reflection
  to reach private members. Keep coverage above the configured JaCoCo thresholds.
- All quality gates must pass locally before a PR is opened. `check` runs Spotless, Checkstyle,
  the tests with the JaCoCo coverage gate, the UI gate and the build-logic tests:

```bash
./gradlew spotlessApply check
```

- Formatting is palantir-java-format (4-space indentation, 120 columns) applied by Spotless;
  Checkstyle (`config/checkstyle/checkstyle.xml`, Google style adjusted) rejects comments,
  unused imports and variables and naming violations. The agent module keeps
  `java.format.enabled=false` next to its coverage ratchet until M1 rewrites it.

- Dependencies are declared in `gradle/libs.versions.toml` only. Resolved versions are locked
  per module in `gradle.lockfile`; after any dependency change run
  `./gradlew dependencies :architrace-api:dependencies :architrace-agent:dependencies :architrace-control-plane:dependencies :architrace-ui:dependencies --write-locks`
  (and `./gradlew -p build-logic dependencies --write-locks` for the build logic) and commit the
  lockfiles.
- UI (`architrace-ui`): TypeScript strict, ESLint with type-checked rules, Prettier, Vitest with
  Testing Library, coverage thresholds 85 %. `npm run check` is the UI gate; Gradle runs it as
  `:architrace-ui:test`, so the command above covers it. Gradle downloads the pinned Node.js
  (`nodeVersion` in `gradle.properties`); for the dev loop use that Node or any Node 22.12+.
  `src/api/schema.d.ts` is generated from the OpenAPI document and never committed. UI
  dependencies live in `architrace-ui/package.json` with `package-lock.json` committed.
- Security: never commit secrets; never weaken scanners to make a build green; treat
  findings from Snyk, OWASP Dependency-Check, CodeQL and Sonar as work items.

## 5. Project facts

- Agent (`architrace-agent`): picocli CLI + Guice. Receives OTLP traces over gRPC, converts
  spans into a service graph, streams graph batches to the control plane over bidirectional
  gRPC. Entry point `io.github.architrace.MainApp`, commands `run`, `dry-run`, `version`; the
  version comes from the jar manifest (`core.BuildVersion`, `dev` outside a jar).
- Versioning (ADR 0006): `architrace.versioning` wraps axion-release; the version is the last
  `vX.Y.Z` tag plus the highest Conventional Commits bump since it (`X.Y.Z-<sha>-SNAPSHOT`
  between tags, `X.Y.Z` on the tag). Tasks `printVersion`, `printReleaseVersion`,
  `releaseNotes`; `gradle.properties` carries no version. The first tag `v0.1.0` is created
  manually by the maintainer.
- Control plane (`architrace-control-plane`): Spring Boot 4 + Spring gRPC. Accepts agent
  streams, answers health, pushes config updates. HTTP `8085`, gRPC `9090`. Persistence:
  PostgreSQL with Liquibase (ADR 0001). Serves the UI bundle (ADR 0004).
- UI (`architrace-ui`): React + TypeScript single-page application, Vite, TanStack Query,
  `openapi-fetch` with types generated by `openapi-typescript` from the Query API document.
  Gradle builds it (`:architrace-ui:npmBuild`, consumable configuration `bundle`), the control plane packs
  the bundle under `static/` and serves it at `/` with a single-page fallback
  (`web.WebConfiguration`, `web.SpaFallbackResourceResolver`); `/api`, `/actuator`,
  `/swagger-ui` and `/webjars` never fall back (ADR 0004).
- API (`architrace-api`): protobuf contract `architrace-agent.proto`
  (`architrace.controlplane.v1`), generated Java in `io.github.architrace.grpc.proto`.
- Query API: OpenAPI 3.1 document `architrace-api/src/main/resources/openapi/architrace-query-api.yaml`;
  the control plane build generates Spring interfaces and `Dto` models into
  `io.github.architrace.control.plane.api` (`openApiGenerate`, never committed). Swagger UI is
  the `swagger-ui` webjar behind `/swagger-ui`; there is no runtime-generated document.
- Demo stack: `otel-test-app/` (Python Flask services + OTel Collector + docker compose).
- Documentation site: Astro Starlight in `documentation/architrace-inteligence`, published
  to GitHub Pages from `main`.
- Quality tooling already wired: Spotless (license header), JaCoCo (85% line/branch/method),
  SonarCloud (`architrace-intelligence`), Snyk. Repository secrets `SONAR_TOKEN`, `SNYK_TOKEN`,
  `PAGES_DEPLOY_TOKEN` exist; variable `SNYK_ORG` exists.
- Local toolchain: JDK 25 lives at `~/.jdks/jdk-25.0.3+9` (default `java` is 21); run Gradle
  with `JAVA_HOME` pointing at JDK 25. `gradlew` is not executable in git, use `sh ./gradlew`
  or `chmod +x gradlew`.
- Pipelines: `agent.yml` (PR checks) and `ci-cd.yml` (main) are the legacy workflows; M0 PR 3
  replaces them with the gated `pr.yml` / `main.yml` flow described on the M0 feature page.
